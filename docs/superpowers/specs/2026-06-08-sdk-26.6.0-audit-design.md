# SDK 26.6.0 Audit — Design

**Date:** 2026-06-08
**Status:** Approved (pending user review)
**Target release:** `v3.2.0` (minor)
**Branch:** `feat/sdk-26.6.0-audit` off `main`

## Goal

Update the MCP server to ride on `@actual-app/api@26.6.0` and remove drift between our `SdkActualClient` adapter and the SDK's current public surface. The discovery step drives every change — we audit what the SDK diff says changed, not the whole adapter.

## Context

- Current MCP server is `v3.1.0`, pinned at `@actual-app/api@^26.5.0`.
- The v2-direct-sdk rewrite shipped to `main`; the adapter lives in `src/client/sdk-client.ts` (~286 lines, ~30 SDK call sites).
- `@actual-app/api@26.6.0` was released 2026-06-01 and adds two public methods (`getNote`, `updateNote`) plus new tracking-budget fields (`budgeted`, `received`, `balance`, `carryover`). Source: [release notes](https://actualbudget.org/blog/release-26.6.0), upstream PR [#7769](https://github.com/actualbudget/actual/pull/7769).
- We currently work around the notes API with `internalSend('notes-save', …)` at `src/client/sdk-client.ts:245-248`. The public methods retire that workaround.

## Decisions (from brainstorm)

- **Scope:** Full audit against 26.6.0, not just version bump.
- **Branch:** `feat/sdk-26.6.0-audit` off `main`.
- **Release shape:** Minor — `v3.2.0`.
- **Schema policy:** Per-finding — for each propagate/adopt-new row in the audit table, user signs off before code lands.

## Design

### 1. Discovery — diff the SDK surface

Install `@actual-app/api@26.6.0` into a scratch location (or under `/tmp` via `npm pack`), extract its public `.d.ts` files, and diff against `26.5.0` (already in `node_modules`).

Produce a structured list of:
- **NEW** — methods or exported types added.
- **CHANGED** — signature or return-shape changes on existing methods.
- **REMOVED** — exports gone.

Persist the raw diff into `docs/superpowers/research/2026-06-08-sdk-26.6.0-diff.md` as evidence so the audit table can be re-derived later.

### 2. Audit — map each diff item to our code

For each diff entry, grep our adapter and classify the finding into one of four buckets:

| Action | Meaning |
|---|---|
| **Absorb** | Adapter accommodates the SDK change internally. MCP tool contract unchanged. No user sign-off needed. |
| **Propagate** | MCP tool input/output schema changes. Needs a CHANGELOG entry and explicit user sign-off in the spec. |
| **Adopt-new** | New SDK method we want to wire in. User sign-off needed. |
| **Skip** | Irrelevant to MCP (UI-only props, app-shell concerns). Brief reason recorded. |

Output: an audit table appended to this spec — one row per finding with columns `(SDK item, file:line, action, rationale)`. User decides every Propagate/Adopt-new row before code lands.

### 3. Known refactor targets (pre-audit)

These are entered into the audit table as starting rows, not bypassing the per-finding review:

- **Notes — Adopt-new.** Replace AQL read + `internalSend('notes-save', …)` at `src/client/sdk-client.ts:240-248` with `api.getNote(id)` / `api.updateNote(id, note)`. Verify `getNote` return shape vs our internal `Note` interface in `src/client/actual-client.ts`. If retiring the last `internalSend` call site, also remove the `ActualLib` capture in `init` and the `internalSend` helper (`src/client/sdk-client.ts:280-…`). Cleanup is a separate commit so it can be reverted independently.
- **Tracking budget — Audit-then-decide.** `src/client/sdk-client.ts:197` calls `api.getBudgetMonth(month)`. If new SDK fields (`budgeted`, `received`, `balance`, `carryover`) appear on its return type, decide whether to surface them in `src/tools/budget.ts` formatted output (Propagate) or hold them in the type but not in the tool response (Absorb).
- **Fire-and-forget transactions — Verify upstream fix.** v2 memory flagged `api.updateTransaction`/`deleteTransaction` as fire-and-forget; integration tests use a 250ms SETTLE. Check 26.6.0 changelog / SDK source for the upstream fix. If fixed, drop the SETTLE in tests; if not, keep the workaround.

### 4. Tests

- Update `FakeActualClient` (`src/client/fake-client.ts`) to model any newly adopted methods. Keep the fake stateful so existing unit tests don't regress.
- Run the full suite (unit + integration) end-to-end. Snapshot the pre-change pass/skip counts on the audit branch, then require the post-change counts to match (no new skips, no regressions).
- If notes integration now exercises `api.updateNote`, the legacy AQL-read path can be removed at the same time (covered by the same path through the public API).

### 5. Release

- Branch: `feat/sdk-26.6.0-audit` from `main`.
- Bump `@actual-app/api` to `^26.6.0` in `package.json`.
- CHANGELOG entries scoped per audit-finding category (Adopt-new, Propagate, Absorb).
- One PR to `main`. `release-please` cuts `v3.2.0`.
- No Docker/CI changes unless an audit finding requires them.

### Out-of-table finding: Task 6 fire-and-forget verification

Not in the typed-surface diff but flagged in the spec for verification: `api.updateTransaction`/`api.deleteTransaction` were documented as fire-and-forget at the SDK handler level (the 250ms `SETTLE` workaround in `tests/integration/transactions.test.ts`).

**Status in 26.6.0:** Still fire-and-forget at the handler level. Verified in `node_modules/@actual-app/api/dist/index.js` — `api.updateTransaction` routes through `send("api/transaction-update", ...)` and the handler returns before the CRDT batch resolves.

**Production impact:** None. The v2 rewrite already documented the resolution in `tests/integration/transactions.test.ts:30-49`: production callers funnel through `writeTool` (`src/tools/shared.ts:35-53`) which wraps every mutation in `withRetriedSync(syncAfter)`, draining pending fire-and-forget messages before the next read.

**Decision:** Keep the test-only SETTLE. No code change.

## Out of scope

- UI-only features in 26.6.0 (Crossover report, custom themes, Sankey, Enable Banking sync, automations UI).
- Rewrites of adapter surfaces the SDK diff didn't touch.
- Rule action templating deprecation (announced for a future release; no code action needed yet).

## Risks

- **Hidden type drift.** Several adapter sites use `as Parameters<typeof api.X>[N]` casts that silently absorb SDK signature changes. Mitigation: grep for the cast pattern and re-verify each.
- **`getNote` shape mismatch.** Public `api.getNote` may return a different shape than our internal `Note` interface assumes (e.g., string vs object). Mitigation: type-level verification before swap; small adapter shim if needed.
- **Integration env regression.** Test container may need 26.6.0-equivalent Actual server image. Mitigation: confirm against `docker/` compose file early; bump base image tag if needed.

## Open questions

None at spec time. Per-finding decisions flow through the audit table during implementation.
